+📌 2026-09-28T10:33+02:00 — **Research conclusion: vWAN IPsec-over-ER primary with Internet-IPsec backup.** Microsoft explicitly supports IPsec/IKE over vWAN ExpressRoute private peering and documents a simultaneous Internet VPN site, but the managed vWAN VPN gateway does **not** expose a tunnel-independent BGP loopback that can carry one adjacency across both underlays. Each VPN link requires a unique underlay IP and BGP peering IP; each link normally builds two tunnels to the active-active gateway instances. Therefore the supported design is separate BGP adjacencies per link/gateway instance, with the ER-carried and Internet-carried paths represented as separate VPN connections when per-path policy is required. Both paths are S2S VPN from the hub router's perspective, so Hub Routing Preference cannot distinguish their underlays; prefer the ER-carried overlay using per-connection AS-path policy (branch prepend or inbound/outbound vWAN route maps) and equal prefix lengths. vWAN VPN BGP uses fixed 60/180-second timers and no BFD; DPD can detect some failures sooner. Pin every IKE endpoint and Azure BGP peer with underlay/tunnel-specific host routes to prevent recursive reachability. Same ASN and router ID on multiple sessions from the same physical CPE are normal; duplicate BGP peer IPs across links are not supported. Exact public operational validation remains unlocated; closest evidence is Microsoft's supported dual-site example and a February 2026 simulated vWAN ER/VPN failover lab using separate FRR routers, plus vendor dual-overlay labs with separate BGP peers.

+📌 2026-09-28T10:46+02:00 — **Third candidate: BGP more-specifics over ER-overlay with static aggregate over Internet VPN.** This is technically viable and gives deterministic preference/failback through LPM: ER BGP advertises component prefixes (for example /24s), while the BGP-disabled Internet VPN site supplies a covering static aggregate (for example /16). When BGP withdraws, the aggregate catches traffic; when BGP returns, the more-specifics immediately win. It requires two separate vWAN VPN Site resources because BGP is a site-level setting that applies to all connections created for that site. The design must assume the configured static site prefixes remain eligible when tunnel connectivity is Not Connected/Disconnected—public docs distinguish resource provisioning from data-path status but do not promise health-based static-route withdrawal—so a failed backup can remain a latent blackhole. Azure offers no SLA/IP-SLA object to condition a VPN-site static prefix on DPD/IKE health; external automation would be required to remove or disable it. Primary failover is still gated by IPsec/BGP detection (fixed 60/180-second vWAN BGP timers, no VPN BFD), and a partial data-plane failure that leaves BGP established will not fail over. Mirror the hierarchy on-prem (ER-learned specifics, Internet-tunnel static aggregate with tunnel/DPD tracking), avoid aggregates containing destinations not truly reachable through the backup, and validate symmetry during the unequal convergence window. Rank below dual-BGP for production resilience, but above manual/static-only designs when the CPE cannot support BGP on the Internet tunnel.
