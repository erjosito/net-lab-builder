# ROOT CAUSE (Niobe's diagnosis, not a fix): BIRD's static route
#   "route 10.60.0.0/16 via 10.60.0.4;"
# is a *recursive* next-hop static route: BIRD requires an existing route to the gateway IP
# (10.60.0.4, in the peered subnet 10.60.0.0/27) inside its OWN route table before it will install
# and export the static route. Azure's subnet-peering fabric delivers packets to 10.60.0.0/27
# transparently at the hypervisor/SDN layer -- it does NOT inject a corresponding route into the
# guest OS's kernel routing table (confirmed: NIC effective-route-table for nic-hub-nva DOES show
# 10.60.0.0/27 as a VNetPeering system route at the Azure fabric level -- see s1-12 -- but "ip route
# show" inside the VM has no such entry, and BIRD's kernel1 protocol, which "learn"s from the kernel
# table, therefore never sees it either). Result: the data plane can reach 10.60.0.4 fine (ping
# proves it), but BIRD's own RIB considers the static route's next hop unresolved, so static_bgp
# never installs the route and therefore never has anything to export toward ARS -- independent of
# whether the azure_rs_x BGP sessions are up or down. This is a BIRD-on-Azure config gap, not an
# Azure platform limitation: the fix (for Tank/Trinity, out of Niobe's scope) is to either add an
# explicit onlink/interface-scoped static route for 10.60.0.0/27 in bird.conf or a
# cloud-init-injected host route so BIRD's kernel-learn protocol has something to resolve against.
#
# SEPARATE FINDING: even if static_bgp resolved, "protocol bgp ce_onprem { ... export none; }"
# means the hub NVA is configured to NEVER advertise anything (including 10.60.0.0/16) directly to
# the simulated on-prem CE peer. Given the CE is peered to vnet-hub via a FULL VNet peering (not
# through the real ExpressRoute/Megaport path -- deviation #1), the CE's only possible route to the
# spoke supernet in this topology is a direct BGP advertisement from the hub NVA. With export none,
# there is no such path even in principle. This looks like a bird.conf authoring gap relative to
# the design's intent, separate from the recursive-route issue above.
