Findings vs Microsoft Learn:
(1) **Dual central-ARS active/standby is a dead-end for a *single* spoke.** Peering constraint "Only one peering can have this flag set to true" (learn.microsoft.com/azure/virtual-network/virtual-network-peering-overview → Gateways/on-premises + AVM `remotePeeringUseRemoteGateways` doc) means a spoke can point to **exactly one** remote-gateway/remote-Route-Server VNet. Automation that flips peerings on outage: for each spoke, delete both peering halves, recreate with the new remote gateway target, wait ~30–120 s per spoke for propagation, then spoke re-learns routes from the new central ARS. RTO is O(minutes) per spoke, not seconds; effective routes reset (all peering-derived NHs churn); this is worse than the 180 s ARS hold ceiling we already accept. REJECT for this lab.
(2) **Regional shared UDR with 0/0 flipped between NVA1↔NVA2 IPs** is technically feasible: a route table is region-scoped but can be associated with subnets in multiple VNets in the same region (same or cross-subscription with perms). Cross-region next-hop = NVA IP works over global VNet peering (only the *Basic* LB frontend restriction remains across global peering per the peering overview doc; NVA IP as NH is supported). Downsides: forward path becomes fully automation-driven (no BGP feedback — a silent NVA hang won't flip the UDR), return path stays BGP → asymmetric-by-construction; scaling adds one UDR per (region, next-hop-family). This is a legitimate simplification over central ARS but abandons the "route-injection via ARS" learning goal. Log as **Follow-up-Lab candidate**, not this-lab substitute.
(3) **Production-canonical (per-hub ARS + NVA overlay + app/DNS failover)** is Morpheus's original alternative — it removes the fourth-region SPOF and matches learn.microsoft.com/azure/route-server/multiregion. But it *removes* the VPN-GW/ARS coexistence + central-ARS + route-maps-preview teaching targets. Correct outcome: separate follow-up lab.
(4) **Native Azure "single-spoke cross-region active/standby NH without another regional dependency" — does not exist.** vWAN routing intent: each vHub is regional; spoke has one hub-attachment. AVNM Routing Configuration (learn.microsoft.com/azure/virtual-network-manager/how-to-create-udr-network-manager) automates UDR deploy across a network group but is a *management-plane* solution over the same regional UDR primitive from (2) — data-plane behavior identical. Cross-region Global LB is inbound-VIP only (TCP/UDP frontend), never a UDR next-hop. Gateway LB is regional (VXLAN-chained to a same-region NVA fleet). Route Server is regional. **Verdict: no native primitive removes the regional-anchor requirement — every option pins one leg to a region.**
(5) **Route-maps split policy for THIS design:** ✅ inbound map on central-ARS→NVA2 peering for NVA2-originated 0/0 (prepend ×N) affects best-path (route-maps preview doc: "Outbound route maps modify route advertisements only and don't influence Azure Route Server's best-path selection, because path selection happens before outbound route maps are applied" → inverse: inbound is pre-best-path). For hub2 local-ARS: spoke prefixes re-originated by NVA2 into hub2 ARS **are BGP-learned** (from NVA's perspective, they are eBGP routes from central ARS), so they *are* route-map-eligible on the NVA→hub2-ARS peering direction. **But**: outbound route-map on hub2 VPN-GW *connection* toward on-prem is **not supported on classic Azure VPN Gateway** — connection-level route-maps exist only on Virtual WAN vHubs (learn.microsoft.com/azure/virtual-wan/route-maps-about). 📌 2026-08-05T10:32:00+02:00 — **Route-map user stories guide created for dual-hub-hubless-region-ars.** File: `labs/dual-hub-hubless-region-ars/route-map-user-stories.md`. Key design-decision findings codified:
(1) **Four-mechanism model** (route visibility A, next-hop selection B, traffic authorization C, topology D) is the correct mental model before applying any routing policy. Route maps operate only on A (BGP advertisement control plane). They do not substitute for NSG/firewall (C) or create topology (D).
(2) **ARS route map eligibility rule** (same-VNet constraint): only BGP peers whose peerIp is within the ARS VNet CIDR are eligible for route-map attachment. This is the root cause of EMP-001 (ars-poland cross-VNet NVA peers rejected). ars-hub1/ars-hub2 NVA peers ARE eligible (NVA1/NVA2 are in their respective hub VNets). ARS VPN GW and ER GW connections are always eligible (co-located in hub VNet).
(3) **"Advertise prefixes only to the NVA subnet" is not achievable via route maps** — this conflates route-table visibility (route maps can help) with traffic containment (NSG/firewall required) with topology (peering/tunnel required). All three mechanisms are needed. Route maps can filter what NVA re-advertises but cannot prevent VMs from sending traffic if a route exists.
(4) **Strongest inter-hub recommendation**: do not add hub1↔hub2 direct peering without UDRs forcing NVA chaining on both sides. An NVA-to-NVA IPsec overlay is the production-canonical inter-hub path (matches learn.microsoft.com/azure/route-server/multiregion). Route maps can then filter which prefixes are visible on the overlay BGP session.
(5) **Priority order for remaining route-map experiments** (verified eligible attachment points): Story H community tagging (ars-hub1/hub2 inbound NVA peering) → Story E on-prem filter (ars-hub1/hub2 inbound VPN GW) → Story D filter infra prefixes (outbound VPN GW) → Story G summarization (requires address redesign first). Each of ars-hub1 and ars-hub2 first-use upgrades trigger ~30 min outage + ~$6/day surcharge (irreversible).
(6) **BIRD/FRR is superior to route maps for cross-VNet scenarios** (no locality constraint, no surcharge, no upgrade, more expressive). Route maps add value when: the peer is local, the team wants GUI observability, or ARS-native community/summarization is needed downstream.

📌 2026-06-15 — **Design C: Single-CR GCP-as-on-prem — the pedagogical centerpiece.** Why Design C is better than Design B for the blog: in Design B, each Cloud Router had exactly one BGP peer (its own MCR), so there was no BGP best-path selection happening at the GCP layer at all — the routing was trivially deterministic. Design C collapses to one Cloud Router with two PARTNER Interconnect attachments (one to MCR1, one to MCR2), making it the first point in the design arc where BGP best-path selection is visible at all three layers simultaneously (GCP CR, Megaport MCR, Azure vHub). The "two layers of asymmetry-hiding magic" that Design B had: (1) geography — each VM happened to be co-located with its preferred CR in the same region, making routing look natural without BGP; (2) single-path — each CR had no alternative path to compare against, so no best-path decision was made. Design C removes both layers. **GCP PARTNER Interconnect with single CR, two attachments:** both attachments on the same CR must use different dge_availability_domain values (DOMAIN_1 and DOMAIN_2) — GCP constraint for multi-attachment configs.
