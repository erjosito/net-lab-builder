📌 2026-06-15 — **Design C: Single-CR GCP-as-on-prem — the pedagogical centerpiece.** Why Design C is better than Design B for the blog: in Design B, each Cloud Router had exactly one BGP peer (its own MCR), so there was no BGP best-path selection happening at the GCP layer at all — the routing was trivially deterministic. Design C collapses to one Cloud Router with two PARTNER Interconnect attachments (one to MCR1, one to MCR2), making it the first point in the design arc where BGP best-path selection is visible at all three layers simultaneously (GCP CR, Megaport MCR, Azure vHub). The "two layers of asymmetry-hiding magic" that Design B had: (1) geography — each VM happened to be co-located with its preferred CR in the same region, making routing look natural without BGP; (2) single-path — each CR had no alternative path to compare against, so no best-path decision was made. Design C removes both layers. **GCP PARTNER Interconnect with single CR, two attachments:** both attachments on the same CR must use different dge_availability_domain values (DOMAIN_1 and DOMAIN_2) — GCP constraint for multi-attachment configs. ASN is 16550 on all PARTNER Interconnect CRs (non-negotiable GCP constraint). MCR1 and MCR2 have different ASNs (65001/65002) so no BGP collision at the CR level. Mech C (vHub Route Maps) is confirmed to NOT affect GCP single-CR outbound path selection — vHub prepend is Azure-internal and not re-exported back through the PARTNER BGP sessions. GCP→Azure path is controlled by Mechanism B (MCR prepend), Azure→GCP by Mech C (vHub Route Maps). Independent levers. **Design D fallback** (if Megaport locked): Linux NVA inside VPC as logical single router, no Megaport change, but weaker blog narrative.
