# Work Routing

How to decide who handles what.

## Routing Table

| Work Type | Route To | Examples |
|-----------|----------|----------|
| Lab requirements & architecture | Morpheus | Scope a new lab, pick topology pattern, decide region & SKU mix, write design block in `labs/<name>/README.md` |
| Azure networking design | Trinity | VNet / subnet layout, NSG / UDR / route tables, peering, VPN / ExpressRoute, Azure Firewall, Private Endpoints, App Gateway / Front Door, name resolution |
| Azure networking knowledge / vault stewardship | Trinity | Read Jose's `AzureNetworking` Obsidian vault before designing a lab; backfill findings, gotchas, anomalies, and API-drift observations into vault notes after Niobe validation completes (pre-cleanup gate). See Trinity's charter "Vault Stewardship" section. |
| IaC authoring & deploy | Tank | Bicep / Terraform modules in `src/`, Azure CLI / PowerShell deploy + teardown scripts, parameter files, `azd` wiring |
| Validation & diagnostics | Niobe | `az network …` show commands, effective routes/NSGs, NSG flow logs, Connection Monitor, traceroutes, log/metric queries, portal screenshots, lessons-learned capture |
| Lab documentation & diagrams | Oracle | Topology / control-plane / data-plane / cleanup diagrams in `labs/<name>/diagrams/`; mermaid (simple, renders natively in GitHub) or drawio (multi-cloud / branded icons); embeds in `README.md` |
| Public blog drafting & publishing | Kid | Write engaging inverted-pyramid blog posts for completed labs; publish to `github.com/erjosito` (rolling `azure-networking-blog` repo by default, or per-lab `azure-net-blog-<lab-slug>` repo). Can back-request scenario tweaks (Morpheus), screenshots (Niobe), command outputs (Tank/Trinity/Niobe), and diagrams (Oracle) to make a post publishable. Signs off (or explicitly waives) before lab is "shipped externally." |
| Cleanup / teardown | Tank | Resource group deletion, soft-deleted key vault purge, dangling public IP cleanup |
| Code review (IaC) | Trinity reviews Tank; Tank reviews Trinity-authored IaC | Cross-check before deploy |
| Scope & priorities | Morpheus | Which lab to build next, trade-offs, when a lab is "done enough" to destroy |
| Session logging | Scribe | Automatic — never needs routing |

## Issue Routing

| Label | Action | Who |
|-------|--------|-----|
| `squad` | Triage: analyze issue, assign one of `squad:morpheus / squad:trinity / squad:tank / squad:niobe / squad:oracle / squad:kid` | Morpheus |
| `squad:morpheus` | Architecture / requirements / scope questions | Morpheus |
| `squad:trinity` | Networking design questions / topology bugs | Trinity |
| `squad:tank` | Deployment failures, IaC bugs, cleanup issues | Tank |
| `squad:niobe` | Diagnostic gaps, missing screenshots | Niobe |
| `squad:oracle` | Missing or stale diagrams, README readability, diagram-source bugs | Oracle |
| `squad:kid` | Blog post gaps; missing screenshots/outputs/diagrams for a publishable post; back-request scenario change for a post-worthy lab | Kid |

### How Issue Assignment Works

1. When a GitHub issue gets the `squad` label, **Morpheus** triages it — analyzing content, assigning the right `squad:{member}` label, and commenting with triage notes.
2. When a `squad:{member}` label is applied, that member picks up the issue in their next session.
3. Members can reassign by removing their label and adding another member's label.
4. The `squad` label is the "inbox" — untriaged issues waiting for Morpheus.

## Rules

1. **Eager by default, but two-stage for new labs.** New-lab dispatch is **two stages**, not one:
   - **Stage 1 (~5–10 min):** Spawn Morpheus alone to produce the **lab card** (≤ 1 page, ≤ 5 KB) — slug, regions, SKUs, ASNs, address plan, KV secret inventory, 1-line mechanism, 1-line scenario list. **In parallel with Morpheus**, run pre-flight probes (haiku, ~30 sec each, see rule #22).
   - **Stage 2 (fan-out):** Once the lab card is locked, spawn Trinity + Oracle + Niobe in parallel. Morpheus expands the full manifest (≤ 15 KB) concurrently. This eliminates the prefix-reconciliation cycle observed in lab #2 (Trinity wrote design with one prefix plan; Morpheus's manifest had another; reconciliation cost ~30 min).
   - Tank is queued — does not start until Phase 4 approval gate clears.
   - For follow-up dispatches within an existing lab (refresh, edit, etc.), spawn directly without the two-stage pattern.
2. **Scribe always runs** after substantial work, always as `mode: "background"`. Never blocks.
3. **Quick facts → coordinator answers directly.** Don't spawn an agent for "what region is the lab in?"
4. **When two agents could handle it**, pick the one whose domain is the primary concern. Networking design = Trinity even if it touches IaC. IaC quirks = Tank even if networking-shaped.
5. **"Team, ..." → fan-out.** Spawn all relevant agents in parallel as `mode: "background"`.
6. **Anticipate downstream work.** Whenever IaC lands, spawn Niobe to draft the validation/diagnostic command list against the deployed shape.
7. **Cost guardrail.** Any deployment proposal larger than ~$50/day should be flagged by the proposing agent and confirmed by Jose before Tank deploys.
8. **Ephemeral-first.** Every lab must ship a teardown path. No lab is "complete" without a working cleanup script. Tank owns this.
9. **Evidence-first.** No lab is "documented" without diagnostic output and portal screenshots in `labs/<name>/`. Niobe owns this.
10. **No hardcoded subscription IDs or tenant IDs — anywhere in the repo.** Not in Bicep `param` defaults, not in Terraform `variable` defaults, not in CLI/PS scripts, not in example commands in READMEs, not in `show-output/` captures. Resolution order in any script: (1) `--subscription` flag → (2) `$AZURE_SUBSCRIPTION_ID` env var → (3) caller's `az account show` context. Niobe redacts subscription IDs that leak in via Azure resource IDs (`/subscriptions/<guid>/...`) to `<SUBSCRIPTION_ID>` before output lands in `labs/<name>/`. Tank enforces at deploy time; Niobe enforces at write-up time; Trinity keeps design specs subscription-agnostic.
11. **No hardcoded secrets — anywhere, ever.** Megaport API key/secret live in the user's Key Vault and are fetched at runtime via `az keyvault secret show`. VM admin passwords (Windows) are prompted from Jose at deploy time — no defaults. ER service keys, storage account keys, SAS tokens, JWTs, and any base64-encoded credentials are stripped from artifacts before commit.
12. **Approval gates.** Two gates per lab, both owned by Morpheus: (a) before any deploy — present resources, regions, time + cost estimate; wait for explicit "yes". (b) before any cleanup — show what will be deleted (dry-run); wait for explicit "yes". Never skip either.
13. **VM SKU region research.** Morpheus runs `az vm list-skus --location <region> --resource-type virtualMachines` and filters out any SKU with `NotAvailableForSubscription` restrictions **before** locking the region in the manifest. B-series IS allowed for lab VMs (B1s / B2s preferred); only escalate to D-series when the test demonstrably needs sustained CPU / RAM. If the cheapest viable SKU in the chosen region is more expensive than B2s, check the next-cheapest region in the same geography first. See Morpheus charter "Region + VM SKU research" section for the exact probe.
14. **Diagram-first.** No lab is "documented" without diagrams in `labs/<name>/diagrams/`. Oracle owns this. Mermaid for simple shapes (renders natively in GitHub via ` ```mermaid ` fences), drawio for multi-cloud / branded-icon topology. Default catalogue for ER + Megaport labs: topology, control-plane, data-plane, cleanup chain. Oracle's first dispatch happens in parallel with Niobe's validation — diagrams don't block on validation completing, only on Tank's deploy completing.
15. **Vault is single source of truth for Azure networking knowledge.** Trinity owns read+write into Jose's `AzureNetworking` Obsidian vault (`C:\Users\jomore\OneDrive - Microsoft\ObsidianVaults\AzureNetworking\`). Before designing, Trinity indexes the vault. Before cleanup (Phase 3.4), Trinity backfills lab findings into the vault — non-optional, blocks cleanup. The vault is **read-only** for all other squad members; any vault-touch by Morpheus / Tank / Niobe / Oracle / Kid / Scribe / Ralph must be requested through Trinity. The vault's own `AGENTS.md` defines the page schema (YAML frontmatter, `Labs/YYYY-MM-<LabName>.md` naming, wikilinks) — Trinity follows it without exception. Forbidden GUIDs (subscription `<subscription-guid>`, tenant `<tenant-guid>`) never appear in vault notes; Trinity sanitization-checks every touched file before declaring done.
16. **Blog-writer back-request authority.** Kid owns public blog publication for completed labs (target: `github.com/erjosito`) and has **standing authority** to back-request artifacts from the squad to make a post publishable: scenario changes from Morpheus, screenshots from Niobe, command outputs from Tank/Trinity/Niobe, additional or revised diagrams from Oracle. Receiving members treat Kid's back-requests as in-scope work, not interruptions. A lab is considered "shipped externally" only after Kid publishes a post **or** explicitly waives publication (waiver recorded in Kid's `history.md`). Kid is dispatched **post-Niobe-validation + post-Oracle-diagrams + pre-Phase-3.4-cleanup**, so the lab is still live and artifact-refresh requests are cheap. Kid does **not** write to `net-lab-builder` itself (commits only to `github.com/erjosito` blog repos) and does **not** write to Jose's Obsidian vault (Trinity-write-only). Every blog post draft is presented to Jose for approval before publication, unless Jose has explicitly waived review for a given post. Same sanitization rules as the rest of the squad: forbidden GUIDs, ER service keys, Megaport credentials, VM passwords never appear in blog artifacts.
17. **Pre-gate editorial review (Kid → Morpheus forward-input).** Kid has **standing advisory authority** to comment on Morpheus's manifest draft *before* the Phase 4 approval gate. Scope is intentionally narrow: (a) does the scenario set surface a teachable result worth publishing? (b) does each scenario's evidence plan produce complete, reproducible artifacts? Kid returns ONE async comment per lab (≤300 words). Kid may **extend** a scenario's evidence plan; Kid may **NOT add a distinct mechanism** (new service, new region, new failure mode) — that remains Morpheus's domain. Kid does **NOT** speak to region selection, VM SKU, cost, or IaC tooling. This is consult-only, no veto: Morpheus retains scope and Jose retains the approval gate. The ceremony is **optional per lab** — if Jose isn't publishing, it's skipped silently (no dispatch, no comment, no logged milestone). See ceremonies.md → "Pre-Gate Editorial Review" for the full agenda + hard rules. Origin: 2026-05-29 governance dispatches; both Morpheus and Kid converged on this mechanism after evidence-grounded analysis of lab #1 (Scenario 2's single-source evidence design for BGP community tagging).
18. **Weekly blog-topic scout (Kid scheduled, between-labs).** Kid runs an autonomous scout pass every 7 days (registered 2026-06-08 via `manage_schedule` with `interval: "1d"` — the tool's hard maximum — and a 7-day debounce marker at `~/.copilot/session-state/kid-last-scout.txt` enforcing the actual weekly cadence; the schedule prompt itself reads the marker, exits silently if <7 days have passed, and writes today's date on a successful run) and surfaces 3–5 candidate Azure Networking topics to Jose for go/no-go. Channel: Teams "Notes to Self" via `agent365-teamsserver-SendMessageToSelf` (primary, no UPN hard-coded — Kid runs as Jose so "self" is Jose); email-to-self via `agent365-meserver-GetMyDetails` + `agent365-mail-SendEmailWithAttachments` (fallback). Quality bar: no doc regurgitation, no "works as designed" verifications — only troubleshooting / corner-case / depth-gap candidates pass the pre-send filter. **Jose-reply routing:** (a) **numeric pick** — coordinator files `.squad/decisions/inbox/<date>-blog-topic-<slug>.md` capturing the picked candidate verbatim, then confirms with Jose before triggering Phase 1 (Rule #12 preserved — no auto-dispatch on pick); (b) **"skip"** — no inbox file, scout resumes next week; (c) **no reply** — silently roll, no stale-candidate batching. **Mode-collision guard:** if Kid is mid-flight on a per-lab dispatch when the scheduled scout fires, coordinator skips the scout for that week. Scope: Azure Networking only (Kid's charter scope is unchanged — no compute / storage / app-platform candidates). See ceremonies.md → "Weekly Blog-Topic Scout" for the full agenda + hard rules, and Kid charter → "Weekly Topic Scout (scheduled, between-labs mode)" for the quality bar + source list. Origin: Jose directive 2026-06-08.

19. **Coordinator pre-fills the Phase 4 gate.** By default the approval gate has ONE question: cost approval. The coordinator pre-resolves these defaults BEFORE issuing the gate (do NOT ask Jose):
    - **Lab lifetime** → manual cleanup (Jose decides when to tear down)
    - **Megaport PoP fallback** → allowed (any Zone-1-equivalent PoP at same price)
    - **VM auth strategy** → auto-detect from KV secret names: if `default-password` exists → password auth; if `vm-admin-ssh-public-key` exists → SSH key. If neither, ask.
    - **GCP credential strategy** → check `gcloud auth list --filter=status:ACTIVE`. If authenticated and project is set → use authenticated session. If not authed, ask (prefer interactive `gcloud auth login` over service-account JSON in KV).
    - **Address-plan arbitration** → Morpheus wins (hierarchy: he owns scope). Trinity refreshes downstream files after gate.
    - **Kid pre-gate editorial** → OFF by default. Opt-in per lab when Jose explicitly says "publishable" or "blog this" at the request. (Lab #2 ran with editorial on by default and the review added ~5 min for marginal value on a routine-shape lab.)
    Escalate to a multi-question gate ONLY when there's a real ambiguity (e.g., cost is borderline and a trim option meaningfully changes the lab; or the user's KV is empty of expected secrets). Origin: Lab #2 (2026-06-15) Phase 4 gate had 6 questions, 5 of which were defaultable.

20. **Output budgets — enforced by charter + model selection.**
    - Morpheus lab card ≤ 5 KB; full manifest ≤ 15 KB.
    - Trinity design.md ≤ 20 KB.
    - Niobe validation.md skeleton ≤ 15 KB.
    - Tank `deploy-log.md` ≤ 10 KB.
    - Kid blog draft ≤ 8 KB (~1500 words).
    Agents over budget on first pass get a sonnet follow-up dispatch to compress. Origin: Lab #2 Morpheus shipped a 40 KB manifest (2.7× budget); Trinity shipped a 40 KB design.md (2× budget) — both took ~3× longer than the budgeted output should have required.

21. **Model defaults locked LOWER for routine work.** Per-charter defaults (see each charter's "Model" section):
    - Morpheus, Trinity → `claude-sonnet-4.6` (default); opus only for genuinely novel topology with no prior `.squad/skills/<pattern>/SKILL.md` match.
    - Tank → `claude-sonnet-4.6` (default); opus only for first-of-its-kind cross-cloud + identity + multi-region with no `src/terraform/<similar-lab>/` to crib from.
    - Oracle → `claude-haiku-4.5` (default — most labs clone a prior diagram set); sonnet only for first-of-its-kind layout.
    - Niobe → `claude-haiku-4.5` for skeleton; sonnet for live validation; opus only for genuinely subtle result interpretation.
    - Kid → `claude-sonnet-4.6` for blog drafts (writing quality matters); haiku for scout pass.
    - Scribe → `claude-haiku-4.5` (always).
    Origin: Lab #2 ran Morpheus + Trinity + Tank all on opus-xhigh by default; total elapsed time was ~2 hr before any deploy. With proper skill-aware defaults, target is ~30 min.

22. **Pre-flight probes run in parallel with Morpheus's Stage 1 lab card.** Coordinator spawns these as fast haiku tasks (~30 sec each) the moment a new-lab request lands, BEFORE Stage 1 completes:
    - `az account show --query id` — verify subscription is set and matches request
    - `az keyvault secret list --vault-name <kv>` — discover actual KV secret inventory (drives the VM-auth and GCP-creds defaults in rule #19)
    - `gcloud auth list --filter=status:ACTIVE --format="value(account)"` + `gcloud config get-value project` — verify GCP CLI is authenticated
    - `gcloud auth application-default print-access-token` — verify ADC (Application Default Credentials) is set up. **This is separate from `gcloud auth list`** — TF's google provider uses ADC, not CLI auth. If this returns "Application Default Credentials are not available," surface to Jose to run `gcloud auth application-default login` BEFORE Tank starts; otherwise Tank pauses mid-deploy. Origin: Lab #2 (2026-06-15) Tank discovered ADC missing only at `terraform plan` time, costing an operator round-trip.
    - `az vm list-skus --location <candidate-region> --resource-type virtualMachines` for each candidate region — feeds Morpheus's SKU decision in the lab card
    Results land in `~/.copilot/session-state/<sid>/preflight.md` for Morpheus and the coordinator to read. If any probe reveals a blocker (KV unreachable, gcloud not authed, ADC missing, candidate region SKU-blocked), coordinator surfaces to Jose BEFORE Stage 1 fan-out so it can be fixed without burning agent time. Origin: Lab #2 KV access bear-trap was discovered by Trinity mid-flight, costing ~10 min of escalation.

23. **Skill-aware routing first, agent dispatch second.** Before any new-lab dispatch, coordinator checks BOTH `.copilot/skills/` AND `.squad/skills/` for a matching pattern. If found, the skill path is included in Morpheus's lab-card prompt as `Relevant skill: <path>/SKILL.md — read and use as starting point.` This turns a from-scratch design into a skill-consult-and-adapt. Origin: Lab #2 produced `.squad/skills/dual-er-symmetry/SKILL.md` — next dual-ER lab should reuse it, not redesign.

24. **GCP: new project per lab, no exceptions.** When a lab uses GCP, Morpheus's manifest MUST specify "create new GCP project" with project ID convention `gcp-<lab-slug-short>-<correlation_id>`. Tank's IaC creates the project (TF-native `google_project` resource OR `gcloud projects create` pre-step in `deploy.ps1`), attaches billing (discovered via `gcloud beta billing accounts list`), enables APIs, and sets `quota_project_id` on the google provider. Cleanup deletes the project (`terraform destroy` of `google_project` OR `gcloud projects delete` in `cleanup.ps1`). Never reuse Jose's existing projects (`familytree-471318` or any other). Origin: Jose directive 2026-06-15 — eliminates cross-lab resource contamination, makes cleanup deterministic, isolates billing per lab. See Morpheus charter "GCP project policy" + Tank charter "GCP project lifecycle" for the full pattern.

25. **Cross-cloud labs: phase the apply, never serialize on one provider.** Multi-provider deploys (Azure + GCP + Megaport, or any combination) MUST use `terraform apply -target=` phasing so a credential / auth / operator block in one provider does NOT gate the others. Tank verifies zero cross-cloud `depends_on` edges in pre-flight (via `terraform graph`); if any exist, escalates as design-impact. The default execution pattern is: Phase A = every currently-unblocked provider in parallel; Phase B = each blocked provider as its blocker clears; Phase C = cross-cloud join resources (ER connections, peerings) last. Auth fallbacks are also Tank-side first-class (e.g., `GOOGLE_OAUTH_ACCESS_TOKEN` env var bypasses ADC when only `gcloud auth login` is present — TF google provider supports this natively, no Jose action required). Origin: Jose directive 2026-06-15 — Lab #2 wasted ~40 min waiting on GCP ADC when Azure + Megaport could have been deploying the entire time. Codified in Tank charter "Cross-cloud independence" section.

26. **Trinity always includes a resiliency analysis in every design.** Every `design.md` Trinity writes must contain an explicit "Resiliency analysis" section enumerating single-failure modes (each network device, each circuit, each BGP session, each control-plane component) with blast radius per segment, firewall-in-path consequence, failover time, and operator action. Mitigations are documented as **idempotent patches** to the v1 baseline (named P1, P2, … with exact TF/CLI deltas, cost impact, residual gaps), dormant until Jose says "apply patch P<n>" — never as redeploys, never as breaking changes. Trinity **does not halt an in-flight Tank deploy** with a `DESIGN-IMPACT ESCALATION` for resiliency findings; the patch catalogue is the mechanism, applied post-deploy at Jose's discretion. The "acceptable for a lab" framing is permitted only when paired with explicit deferral text and a pointer to the patch catalogue. Origin: Jose directives 2026-06-15 — *"Trinity should always consider resiliency"* + *"Do not pause Tank, let him finish, and potentially patch the deployed environment."* Codified in Trinity charter "How I Work" rule #7.

27. **ER private peering: dual-VXC per circuit, always.** Every ExpressRoute circuit in every lab is deployed with **two** Megaport VXCs (primary + secondary peering endpoints at the MSEE), never one. Validation: `bgpState=Established × (2 × circuit_count)`. Tank's pre-`apply` check: `terraform state list | rg megaport_vxc` must show 2× the circuit count. Trinity's design.md template includes both primary and secondary peer `/30` allocations from each circuit's Azure-side `azurerm_express_route_circuit_peering`. Single-VXC ER deploys give degraded HA — `serviceProviderProvisioningState=Provisioned` still reports OK because the primary peer is up, but the entire secondary peering port is unbound and resiliency validation breaks. Origin: Jose directive 2026-06-15 — caught at lab #2 validation when only one of two MCR↔ER connections showed active per circuit. Codified in Tank charter "ExpressRoute private peering: ALWAYS dual-VXC" section.

28. **Patch tfvars: carry forward `*_override` values; inspect the plan, never blind-apply.** When Tank applies a `-target=` patch against live TF state, every `_override` input that was set in the active deploy tfvars (`correlation_id_override`, `password_override`, any user-supplied random seed) MUST be carried into the patch tfvars unchanged. Pre-apply checklist: (1) `Compare-Object` patch tfvars against active tfvars — every `_override` matches; (2) `terraform plan -out=tfplan` then `terraform show tfplan | rg '(destroyed|replaced)'` — expect ZERO destroys of non-target resources; (3) only then `terraform apply tfplan`. A destroy of any resource Tank wasn't targeting = abort the patch, fix tfvars, re-plan. Origin: Lab #2 secondary-VXC patch (2026-06-15, tank-1) — `correlation_id_override` was omitted; `random_id.correlation.hex` would have re-seeded and the plan would have destroyed the entire RG. Caught at plan-show step. Codified in Tank charter "Patching live TF state" section.

29. **Resiliency patches: multi-path BGP evidence, before/after pair (active fault injection is OPT-IN).** When Trinity flags a SPOF and the operator approves a patch (P1/P2/…), Niobe captures the unmitigated state on the **live** v1 env BEFORE Tank applies the patch (full three-layer route collect filtered for the affected prefix family, path matrix table showing single-path-only). After Tank applies, Niobe re-runs the IDENTICAL capture set. For BGP-based patches, the explicit assertion is: on each affected device, the same prefix appears in the routing table with ≥2 distinct AS-paths / next-hops / BGP neighbours where it had 1. **Active fault injection is opt-in, not default** — only run when the patch claim is about convergence time or behavior under failure, not when the claim is "there are now N paths where there was 1". Output lands in `design.md` as paired subsections (`§1.6.x Before-patch evidence` + `§1.6.x+1 After-patch evidence`). Origin: Jose directive 2026-06-15 — *"We don't need to run a SPOF test, just to verify that routing should cover for it. For example, that the Google router receives 2 routes for each spoke VNet, one from each MCR."* Codified in Niobe charter "Resiliency captures" section.

30. **Every design studied gets documented with evidence-based verdict.** Every network design a lab investigates — recommended AND not-recommended (anti-patterns, SPOFs, asymmetric topologies) — gets a first-class entry in the lab's `README.md` under `## Designs studied`. Per-entry: status badge (✅ Recommended / ⚠️ Not recommended / 📚 Teaching-only), 1-sentence verdict, what-it-is paragraph, evidence links (`show-output/` paths, `design.md` section refs, screenshots), why-this-verdict paragraph grounded in cited evidence (no hand-waving — quote the routing table or BGP-peer count or connectivity matrix), and use-when / avoid-when bullets. Morpheus enumerates every candidate in his manifest's `## Designs studied` section up-front (charter "How I Work" rule #9); Niobe scaffolds the README from that list and fills verdicts as captures land. A design with verdict "not recommended" is NOT a failure — it's the documented anti-pattern future readers reference. Lab is not done until every enumerated design has a verdict + evidence. Origin: Jose directive 2026-06-15 — *"Every design is valuable. Either because it is a recommended design or because it isn't. For every design Niobe should collect proof of why the design is or is not desirable, document it, and move on."* Codified in Niobe charter "Local README structure" + Morpheus charter "How I Work" rule #9 + `labs/README.md` convention table.
